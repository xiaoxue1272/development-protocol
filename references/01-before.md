# 开发前 · 批准闸门

## 规则

**未获批准，绝不改动任何文件。**

在写下一个字节之前，先给方案，拿到明确确认。

**读是允许的，写不是。** 这条边界把"调研"和"动手"分成两个阶段。不看就出方案是瞎猜；
一边看一边改是另一种失控——全貌还没搞清，第一个修改就已经落盘了。

## 为什么需要它

代码库是用户的，不是你的草稿纸。没有闸门，典型结局是带着假设往下冲、改出用户没要求的东西，
再花更多时间解释和回滚。闸门不是拖延，是让错误在消耗信任之前被拦下。

## 何时触发

判据只有一条：**这次回应完成后，用户请求所指向的文件会不会和现在不同。**

- **会** → 闸门激活，先出方案。
- **不会**（只回答、只解释、只分析）→ 不需要方案。
- **拿不准** → 按"会"处理。多问一次的成本，远低于擅自动手的成本。

流程自身的工作文件（开发日志、忽略配置）不在判据范围内——它们不是用户请求指向的东西，
记录本身不构成对用户资产的改动。

不要靠关键词判断。用户不必说出"改"或"修"——"这按钮位置不太对""这段逻辑好像有问题"
"能不能加个导出"都不含动词化的修改指令，但都在要求你动文件。
反过来，"你改的那个方法是怎么写的？"含着"改"字，却只是提问。

**判据是结果，不是措辞。**

## 执行流程

```
DETECT   识别为改动请求 → 闸门激活
ANALYZE  读涉及的文件，搞清当前状态（可读，不可改）
PRESENT  按下方格式输出方案
WAIT     什么都不做。等无保留的放行（判据见「什么算批准」）
EXECUTE  仅在明确批准后开始动手，用任务清单跟踪进度
```

`WAIT` 是最容易失守的一步。它的意思是：方案这条消息发出后就结束，不要在同一轮里顺手改点什么。
换句话说，**「等批准」＝结束本轮输出、把控制权交回用户**；不是在同一轮里挂起，也不是边等边动手。
"方案我已经给了，用户显然会同意"不是批准。

## 方案格式

四段，缺一段就要补。篇幅可随改动大小伸缩，骨架不能省。

```
## 执行方案

### 当前状况
- 涉及模块：
- 现有逻辑：（一句话说清当前代码在做什么）

### 改动清单
| 文件 | 操作 | 内容 |
|------|------|------|
| <文件路径> | 新增 | <新增什么> |
| <文件路径> | 修改 | <改什么、为什么> |

### 改动后状况
- 新增/变化的能力：
- 影响范围：（哪些已有功能会被牵动）

### 风险
- 是否影响现有功能：
- 是否涉及数据或状态的变更：
- 是否有其他模块需要配合：

---
请确认以上方案，确认后开始执行。
```

四段各防一种错：
**当前状况**防"我以为代码是这样"；**改动清单**防"改着改着改到计划外"；
**改动后状况**防"用户以为你要做的和你要做的不是一件事"；**风险**防"改完才发现有联动"。

一行改动也要出方案，但方案可以只有三行。闸门的标准是"用户能否据此判断你要干什么"，
不是"方案够不够长"。

## 什么算批准

判据不是"用户说了哪个词"，而是：**这条回复里有没有任何一点保留。**

- **无保留的放行** → 批准。用户读了方案，表达了可以继续的意思，不附条件。
- **带保留的回应** → 不是批准。哪怕语气很肯定，哪怕只附了一个小疑问：方案要改、
  要先看别的、范围要缩、时间要等。保留本身就是"先别动"。
- **没有回应** → 不是批准。沉默不是同意，是不在场。
- **用户提了新问题** → 不是批准，是新需求。先回答，再重新出方案。

下面这些形态用来说明上面四条长什么样，**不是清单**——依据始终是有没有保留，
而不在于有没有命中某个词：

| 放行 | 实质 |
|---|---|
| "行，就这么办" / "可以，按你说的" | 无保留 |
| "开始吧" / "go" / "approved" | 无保留 |

| 不是放行 | 实质 |
|---|---|
| "行是行，不过……" | 有保留，保留的那部分先谈 |
| "等一下，我先看看 X" | 有保留 |
| "这个方案有问题" | 有保留 |
| "顺便把 Y 也改了" | 范围变了，等于没批 |
| "嗯" / "我考虑下" / 沉默 | 无立场，按未批准处理 |

"用户看起来很清楚自己要什么"**不是**豁免理由。真正要防的正是这种情况：用户说"加个导出",
他脑子里是一个按钮，你脑子里是一整套异步任务队列。

## 豁免

只有两种：

1. 用户明确说"不用方案了，直接做"。
2. 请求纯信息性，不涉及文件变更。

除此之外没有第三种。**紧急不是豁免**——急中出错要花更多时间收拾。

## 反模式

| ❌ 错误 | ✅ 正确 |
|---|---|
| "很简单，我直接改了" | 一行也要出方案 |
| "先改一版，再问好不好" | 先问，后改 |
| "边改边说明" | 说明和修改是两个阶段 |
| "有 bug 太急，跳过闸门" | 紧急不豁免 |
| "用户说了加导出，我加就是了" | 用户可能不知道"加导出"意味着什么 |
| "方案在脑子里想过了" | 想过 ≠ 说过；用户看不见你的脑子 |

## 获批之后

批准到手就进入 `references/02-during.md`。别在同一轮把"批准"和"改完全部清单"一次做完——
一次一个问题，改一条、验一条、记一条。
