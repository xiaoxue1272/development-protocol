# 开发中 · 实现纪律

方案获批之后、说出"完成"之前，这段时间的行为规则。核心是三件事：别贪多、别靠记忆、别跳过验证。

## 一、一次只改一个问题

每个交互只推进一个点。哪怕方案清单里有五条，也一条一条来：改完第一条 → 测 → 验 → 记，
再开第二条。

为什么这不是低效：混着改，出问题时你无法定位是哪一处引入的，只能逐个回滚试探；
用户也没法单独判断某一条方案对不对，只能对整个包打通过或打回。一次一个，
错误的影响面就被限制在一个改动里。

用户一次丢来十条清单时，正确处理不是"我全改了给你一个大 diff"，而是
"第 1 条我按这个方案改，其余九条排在后面"。

## 二、先读再改

修改前读**完整**文件内容，不要只看搜索命中的那几行。

- **以本地代码为准**，不凭记忆、不凭"通常写法"。你记忆里的代码永远是"某个版本"，
  不是你手上这个版本。这个仓库可能已经改过命名、改过分层、改过返回结构。
- **读完整文件**而不是读片段。上下文决定这段代码该怎么改：方法在类里的位置、
  周边已有工具方法、异常处理约定、这层的职责边界，都在你看不到的行里。
- **跟随现有风格**。同一个项目里出现两种写法，比任何一种"不够优雅"的写法都更糟。

判断标准：你能不能说出这个文件里**已有**的同类逻辑是怎么写的。说不出，就是还没读懂。

## 三、每改必验

每个改动完成后，用与改动相称的方式验证，并留下证据。

- **有测试框架**：测试放在**项目自己的约定**里——先看现有测试住在哪、怎么命名，跟着放；
  没有既有约定时与被测对象就近，并在方案里说明选在哪、为什么。每个用例覆盖三段：
  前置条件 → 操作 → 预期结果。最后跑**全量**，不只看新加的那一个：新测试通过、
  老测试被打挂，是最常见的事故形态；只跑新测试等于只检查自己写的那一半。
- **没有测试框架**（纯文档、纯配置、纯静态资源）：做能复核的检查并留下结果——
  复读改过的文件全文、对照方案逐项核对、确认改动只落在约定范围、检查引用的路径是否真实存在。
  做法见 `03-after.md` 的「替代证据」。
- **拿不准算哪类**：先看仓库里有没有测试目录和测试命令，没有就按第二类走，别硬造一个测试框架。

### 与 TDD 的先后关系

两种做法看起来冲突：TDD 要求"先写测试并看它失败"，工程惯例是"改完再补测试"。裁决如下：

**能先写测试就先写。** 先写、先跑、亲眼看它失败，你才知道这个测试测的是对的行为——
否则你可能写了一个永远为真的断言，它从第一天起就没在检查任何东西。

**拿不到失败态时，允许先改后补测，但必须写明为什么。** 典型情况：改的是配置、是纯声明、
是已有行为、是第三方接口。此时判断标准是：如果你无法描述"这个测试失败时输出长什么样"，
那它大概率不是有效测试，只是把实现抄了一遍。

## 四、实现期的常见走偏

| 走偏的念头 | 实际情况 |
|---|---|
| "顺手把这个也改了" | 计划外的改动不会被验证，也不会被记录 |
| "这个文件我大概知道内容" | 大概知道 = 不知道；版本可能已经变了 |
| "构建过了应该就没问题" | 构建过 = 语法对，不等于逻辑对 |
| "先跑起来，测试回头补" | 回头通常不会来；补测的成本比当时高得多 |
| "老测试挂了但跟我的改动无关" | 要么是你的改动影响了它，要么它本来就在飘——两种都得查 |
| "用例写太多了，能过就行" | 用例的价值在覆盖边界，不在数量好看 |

## 五、这一段收尾时自检

进入 `03-after.md` 之前，先回答这四个问题：

1. 改动和获批的方案**逐条对得上**吗？有没有计划外的东西混进去？
2. 涉及的文件是否**都完整读过**，风格是否与现有代码一致？
3. 每个改动是否有对应验证证据——测试全量跑过，或按「替代证据」逐条检查过？证据能贴出来吗？
4. 开发日志是否已经追加，包括**跳过的项**和原因？（用户请求所指向的文件零改动时不写，判据见 `references/03-after.md`）

四个问题有一个答不上来，就别进入下一阶段——那不是在验证，那是在给自己找台阶。
