# 开发后 · 验证闸门与变更记录

## 规则

**没有新鲜的验证证据，不得声称完成。**

不能以任何完成类表述收尾——"完成""搞定""没问题""可以提交"，以及它们的任何变体——
除非你刚跑过这个项目的构建/测试命令并看到通过；项目没有可跑命令时，按「替代证据」
取得并检查过对应证据。

判据不在于你用的是哪个词，而在于**这句话的依据是什么**：是刚看过的输出，还是你的推断。
同一个词，有输出支撑就是结论，没输出支撑就是猜测。

你的信心不是证据，只有刚跑出来的输出是证据——笃定的语气和跑没跑过无关。

## 执行流程

```
DETECT   我准备给这次改动下结论了 → 闸门激活
IDENTIFY 这是什么项目？构建命令和测试命令是什么？从项目文件里读，不要猜
         ├─ 有可跑命令：走「命令验证」
         └─ 没有可跑命令：走「替代证据」，不编命令凑数
命令验证 RUN    执行完整命令。全新跑一遍，不吃缓存、不复用五分钟前的结果
         READ   看退出码，数错误数，数失败数
         REPORT 全绿："Build: ✅ exit 0 / Tests: ✅ 12/12 passed"
                有错："Build: ❌ 3 errors，<文件>:<行号> <错误摘要> → 正在修"
替代证据 CHECK  复读改过的文件、对照方案逐项核对、确认实际字节变化，逐条留下结论
         REPORT 贴出上述检查的实际结果与结论，不套 Build/Tests 形态
CLAIM    所选路径的证据齐了，才可以带证据说"完成"；证据不全就只说完成度
```

## 验证命令从哪来

不要按项目类型套模板，也不凭经验猜。命令只有一个来源：**这个项目自己**。

去找这个项目的构建配置、持续集成配置、任务运行脚本，以及 README 里的开发说明——
它们定义了哪条命令叫"构建"、哪条叫"测试"。

找不到，就把"这个项目没有可跑的构建或测试命令"当作结论说出来，转去走「替代证据」，
假命令跑出来的"通过"，比没有验证更糟。

## 必须报告的形态

有可跑命令时，贴命令输出：

```
✅ Build: <构建命令> → exit 0
✅ Tests: <测试命令> → 12/12 passed, 0 failures
```

没有可跑命令时，贴替代证据，不套上面的形态：

```
✅ Checks: 复读 <文件> → 与方案第 2 条一致
           对照方案 → 4/4 条逐项核对通过
           实际字节变化 → <文件> 3 处，均在改动清单内
```

失败时同样要贴真实输出，而不是只说"有点问题"：

```
❌ Build: <构建命令> → <文件>:<行号>
   <错误原文>
   → 正在修复，稍后重跑
```

只贴证据，不叙述过程。"我仔细检查了""反复确认过"这类话没有信息量——读者要的是命令、
退出码、失败数，或逐条检查的实际结论，不是你做过什么动作。

## 替代证据（没有可跑命令时）

纯文档、纯配置等没有构建/测试命令的项目，用能被复核的动作代替命令输出：

1. 复读改过的文件全文，确认写进去的就是方案里写的。
2. 对照方案逐项核对改动清单，逐条标"符合 / 不符合"。
3. 看实际字节变化，确认改动只落在约定范围。
4. 检查引用的路径、命令、文件名是否真实存在。

逐条留下实际结果，缺一条就只说完成度。它们替代的是"退出码为 0"这个证据位，
不是降低标准；"我检查过了"仍然不算证据。

## 没有例外

"没有例外"只指一条：不得在没有新鲜证据时称完成。证据分两类，齐了就算数——
有可跑命令就贴命令输出，没有就按「替代证据」逐条留下实际结果。
"没有命令可跑"不是"没验证"的借口，也不是"已完成"的理由：走对应那类证据，再谈完成度。

判据是依据，不是词汇：换一个同样模糊的说法绕开下面的词，问题照旧存在。

| 还没有证据的说法 | 缺什么 |
|---|---|
| 应该没问题、看起来好了、seems to work | 去取新鲜证据（命令输出或替代证据），贴结果 |
| 改完了、搞定了、I think it's done | 改完 ≠ 验证过 |
| 改动很小不用测 / 五分钟前刚跑过 / 用户很急 / 测试太慢 | 代码会变，急和累都要先验证 |
| 静态检查干净 | 静态检查不是构建，更不是运行 |
| 先告诉用户，稍后验证 | 先验证，后告知 |

## 变更记录

有两份记录，性质完全不同，别混在一起写。

### 一、开发日志：必写，由我自己维护

每次改动后追加，**包括跳过的项**。它的用途是溯源、追查、事后调整，不是交付给用户看的东西。

**不写的情况只有一种：用户请求所指向的文件没有发生任何变化。** 纯排查、纯验证、只读了一遍代码、
只跑了一次检查命令就收尾——这些不写。日志值钱的地方在于"变了什么"，零改动时它只会把
真正的记录淹掉。判据：这次用户请求所指向的文件有没有字节变了；`.dev-protocol/` 这类流程
自身的工作文件不计入，否则写日志本身会再触发一条日志。

**为什么必写**：跳过项不记录，下次会被重新发现、重新争论一遍，等于把同一份调研成本付两次；
决策理由不记录，三个月后只能看到"改成了这样"，看不到"为什么没选另一条路"。
对话不是存储——它会被压缩、会被截断，写下来的才算存在。

- **位置**：项目根 `.dev-protocol/changelog.md`，按时间顺序追加。
- **默认不进版本库**：这是本地的开发台账，不是交付物。项目用版本控制时，按它自己的忽略机制
  把 `.dev-protocol/` 排除——git 写 `.gitignore`、Mercurial 写 `.hgignore`、SVN 设
  `svn:ignore`、Perforce 进 P4IGNORE，别的工具照它自己的规则来。
  告诉用户一声文件在哪、已排除；用户明确要求入库时再撤掉那条忽略规则。
  不用版本控制的项目跳过这步，报告里注明即可。
  不必等批准：批准判据看的是用户请求所指向的文件，`.dev-protocol/` 是流程自身工作文件，
  本就不在判据范围内。

每条包含：

- 时间、问题编号、严重程度、问题描述
- 状态（已修复 / 跳过）
- 跳过原因（如适用）
- **决策与理由**：选了什么、否掉了什么、为什么
- 改前 / 改后对比
- 配置项（如有）
- 涉及文件表
- 遗留风险、后续待办、未经测试的分支
- 验证详情表

验证记录固定格式（有可跑命令记命令输出，没有可跑命令记逐条检查结果，两者都写"检查项"）：

```
| 检查项 | 前置条件 | 操作 | 预期结果 | 实际结果 | 状态 |
|--------|----------|------|----------|----------|------|
| 分页参数为空 | 不传 page/size | 调用列表接口 | 使用默认值 1/20 | 返回 1/20 | 通过 |
| 方案第 2 条 | 03-after.md 已改 | 复读全文 | 与方案一致 | 一致 | 通过 |
```

「决策与理由」最容易被省略，也最有价值：代码能告诉你做了什么，
只有这一条能告诉你当时为什么没做别的。

### 二、用户的 changelog：默认不写

项目里的 `CHANGELOG.md`、发布说明、更新日志属于用户资产，**默认不动**。

不要因为"改了代码就该记一笔"就自动往里写。那份文档面向用户和版本发布，
格式、颗粒度、语气都由用户决定，不由你决定。

要写就先问一次。问的时机：涉及对外可见的行为变化、版本发布，
或用户自己提到要发版 / 要写说明。问法一句就够——"要不要一并更新 CHANGELOG？"
用户说要，就按项目既有格式写；用户没表态，不写。

### 三、记录强度怎么定

不是每次都要写满九个字段。改一个拼写和改一个跨模块行为，详略差十倍都正常。
判断标准只有一条：**三个月后你（或接手的人）能不能靠这条记录判断当时发生了什么、为什么这么做。**
能，就够了。
